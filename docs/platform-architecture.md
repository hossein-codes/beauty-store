# معماری پلتفرم — اپلیکیشن در برابر وب

> **قانون اصلی پروژه:** موبایل نسخه‌ی باریک‌شده‌ی دسکتاپ نیست.
> موبایل یک **اپلیکیشن** است، دسکتاپ یک **وب‌سایت**.
> هر دو از یک سیستم توکن مشترک تغذیه می‌شوند تا وقتی اپ نیتیو ساخته شد،
> دقیقاً شبیه نسخه‌ی موبایل وب باشد.

## نقاط شکست (Breakpoints)

| عرض | پوسته | ناوبری | چیدمان |
|---|---|---|---|
| `< 768px` | App Shell | نوار پایین (Tab Bar) | تک‌ستونه، ریل‌های افقی |
| `768–1023px` | Hybrid | نوار پایین | گرید چندستونه |
| `≥ 1024px` | Web Shell | هدر بالا | گرید + کانتینر وسط‌چین |

این اعداد در دو جا تعریف شده‌اند و **باید هماهنگ بمانند**:

- `src/styles/tokens/platform.css` (برای CSS)
- `src/hooks/use-breakpoint.ts` (برای JS)

> CSS اجازه نمی‌دهد متغیر سفارشی داخل شرط `@media` استفاده شود، بنابراین
> عددها ناچاراً تکرار شده‌اند. این محدودیت مرورگر است، نه انتخاب ما.

## چرا هر دو پوسته رندر می‌شوند؟

`AppShell` همزمان هدر موبایل، تب‌بار و هدر دسکتاپ را رندر می‌کند و CSS
دقیقاً یکی را نشان می‌دهد.

**چرا با JS شرط نگذاشتیم؟** چون سرور ویوپورت را نمی‌شناسد. اگر بر اساس
`matchMedia` تصمیم می‌گرفتیم، یا اولین رندر پوسته‌ی اشتباه بود، یا
hydration mismatch می‌گرفتیم. هزینه‌ی این تصمیم مقداری مارک‌آپ اضافه در
DOM است که ارزشش را دارد.

`display: none` عنصر را از tab order و درخت دسترس‌پذیری هم حذف می‌کند،
پس اسکرین‌ریدر ناوبری را دوبار نمی‌خواند.

برای ویجت‌های سنگین (مثل مگا‌منو) از `useIsDesktop()` استفاده کنید تا اصلاً
mount نشوند — ولی هرگز برای چیدمان اصلی.

## ⚠️ تله‌ی Cascade

`.nav-app { display: none }` و `.app-tabbar { display: flex }` هر دو
specificity برابر `0-1-0` دارند. یعنی **ترتیب import تعیین‌کننده است**.

چون `utilities/platform.css` قبل از `shells.css` ایمپورت می‌شود، اگر
`.app-tabbar` خودش `display` تعریف کند، برنده می‌شود و تب‌بار روی دسکتاپ
هم نمایش داده می‌شود.

**راه‌حل:** هر عنصر پوسته، visibility خودش را در `shells.css` تعریف می‌کند.
کلاس‌های `.nav-app` / `.nav-web` روی عناصر باقی مانده‌اند ولی صرفاً
نشانه‌گذاری معنایی‌اند.

این باگ بی‌صداست — روی یک صفحه‌ی بلند دسکتاپ، تب‌بار ته صفحه به‌راحتی از
چشم بازبین جا می‌ماند. برای همین تست خودکار دارد:

```bash
npm run dev          # در یک ترمینال
npm run check:shell  # در ترمینال دیگر
```

## Safe Area (ناحیه امن)

برای اینکه `env(safe-area-inset-*)` مقدار واقعی برگرداند، **حتماً** باید
`viewportFit: "cover"` در `src/app/layout.tsx` تنظیم باشد. بدون آن همیشه
صفر برمی‌گردد و نوارهای ثابت زیر ناچ یا home indicator می‌روند.

توکن‌های موجود:

```css
--safe-top     /* ناچ / status bar */
--safe-bottom  /* home indicator */
--safe-start   /* لنداسکیپ */
--safe-end
```

هر عنصر `position: fixed` باید یکی از این‌ها را در نظر بگیرد.
`--app-header-total` و `--app-tabbar-total` ارتفاع نوار + ناحیه امن را
با هم حساب می‌کنند و `.app-content` از همان‌ها برای padding استفاده می‌کند —
پس تغییر ارتفاع نوار هیچ‌وقت نیاز به دست‌زدن به صفحات ندارد.

## چرا اسکرول داخلی نداریم

وسوسه‌انگیز است که `.app-content` را `overflow-y: auto` کنیم تا شبیه اپ شود.
**این کار را نکنید.** اسکرول‌کانتینر داخلی این‌ها را می‌شکند:

- مخفی/ظاهر شدن نوار آدرس مرورگر موبایل
- بازیابی موقعیت اسکرول هنگام بازگشت
- هر `position: sticky` داخل صفحه

به‌جایش با padding برای نوارهای ثابت جا باز می‌کنیم.

## آماده‌سازی برای اپ نیتیو

هنوز تصمیم نگرفته‌ایم اپ با چه تکنولوژی ساخته شود، پس معماری طوری چیده شده
که هر سه مسیر باز بماند:

- **WebView / Capacitor** — همین کد بدون تغییر اجرا می‌شود. پوسته‌ی موبایل
  دقیقاً همان اپ است. `html[data-native="true"]` را از سمت نیتیو ست کنید.
- **React Native / Flutter** — توکن‌ها باید به JSON/Dart اکسپورت شوند تا رنگ
  و فاصله‌ها یکی بماند. چون همه‌چیز از CSS custom property می‌آید، این کار
  یک اسکریپت ساده است (هنوز نوشته نشده).

هیچ مقدار hard-code شده‌ای در کامپوننت‌ها نیست — این چیزی است که مهاجرت را
ممکن می‌کند.

## PWA

فعلاً راه‌اندازی نشده (طبق تصمیم شما). وقتی خواستید:

1. `public/manifest.json` با `display: "standalone"`
2. آیکون‌های ۱۹۲ و ۵۱۲ پیکسل
3. `metadata.manifest` در layout

توکن `--app-is-standalone` از قبل آماده است و در حالت standalone فعال می‌شود.
